## 上限の判断

[MyDNS.JPの公式案内](https://www.mydns.jp/)には最終通知から1週間の保持期間があります。
最大3日＋確認周期最大1日なら通常の次の確認は約4日目、1回失敗した後の再試行は約5日目です。各周期の処理時間は別に加わります。
無期限の通信障害、大量のアカウント、ホスト停止まで含めた期限保証ではありません。既定の1日・確認5分は変更しません。

[curl公式資料](https://curl.se/docs/manpage.html#--max-filesize)では8.4.0より前の長さ不明応答にmax-filesizeが効かないと説明されています。
そのためmax-filesizeだけの修正は採用しません。Linuxシェルのulimitをcurlの子プロセスだけに設定し、ファイル書き込みを制限します。
設定不能なら通信せず失敗扱いです。64 KiBは短いMyDNS成功HTMLに余裕を持たせた上限ですが、実サービスの応答が将来大きくなれば再検討が必要です。
NASのメモリ不足やホスト停止を再現したわけではありません。

## 検証範囲と別途検討

既存CIと追加試験の全9ジョブが成功しました。実curlの対象はUbuntu 22.04・24.04とAlpineです。
その後、v1.10.1のSynologyとUbuntu 24 VMの記録を確認しました。[今回の確認範囲](../testing.md#v1101の確認範囲)を参照してください。ARMは未確認です。v1.10.0の記録を修正版の結果へ読み替えてはいません。

R-007はmain `ecf4bd2105c2986a8aea38ebbf6b14c8ae2302ad` でも妥当でした。コードは1.10.1ですが、READMEに未マージ案内、現行導入・復帰手順に1.10.0の成功判定が残っていました。取得先のmain、同じ一式の配置、最新STARTUPの照合を揃えました。実装の変更は不要で、N1〜N3・R1〜R3の修正は維持しています。

- ARM64：公開イメージの対応アーキテクチャを広げる前に、実行試験を追加する価値がある。今回のamd64検査とは別。
- Alpineの版：本番のlatestと一部復帰試験の固定版は一致しない。版の固定・更新方針と試験マトリクスを次に検討する。今回の容量試験は本番と同じlatestも含む。
- Synologyの親フォルダーACL：rootで実行する監視スクリプトの置き換え可否に関係する。所有者・chmodだけではNAS固有の親ACLまで確認したことにならない。NAS側での確認が必要で、現在侵害可能と確定したものではない。
